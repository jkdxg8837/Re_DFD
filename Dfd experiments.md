## 1. Background (understand, don't implement)

**Problem.** DFD increases the diversity of a DMD student by using more diverse data to spread out and shift the student's over-concentrated distribution. However, DFD's theoretical construction only works in practice with synthetic data input. Real-world data, which satisfies the theory equally well and is more diverse, has no effect inside the DFD framework.

**Why it fails.** The theory makes several approximations and loose bounds, ignoring how the error constants affect the already fragile DMD distribution:
- A.1 (zero-mean): holds only when the generator already sits at the optimum (matches p_real); says nothing about points far from the optimum. Zero mean also does not control variance — a high-variance p_real can make the regularizer ineffective.
- A.2 (MSE upper bound between the DFD loss and the DMD KL, under 3 conditions): condition 1 (gap δ between G and p_real), condition 2 (bound on x_t vs. x̂_t / Lipschitz), condition 3 (Jensen converts G's parameter-space gradient into value space, constant B) are each loose; their product can be huge, so the "controlled approximation" may lead to a sub-optimal point.

**Research question.** When post-training brings in higher-variance real-world data, how should the constraint term and the coupling between the real score and the fake score be designed so that post-training injects variety with **zero mean and small variance**?

**Note:** the "real data" in the DFD paper (ViPE-Wild) is actually **video generated by Wan2.1-14B** `[VERIFIED]`, i.e. "synthetic data" in this project's terminology.

### 1.1 What DFD actually does in code `[VERIFIED, fastgen/methods/distribution_matching/dmd2.py]`

In `DMD2Model._student_update_step`, when `model.post_train=True` and `torch.rand() < model.gen_real_replace_prob`:

```python
gen_data_teacher_score = gen_data + (real_data - gen_data).detach()   # whole batch replaced (straight-through)
forward_kl_ensemble = True
```

Then:
- `perturbed_data = forward_process(gen_data, eps, t)`; `perturbed_data_teacher_score = forward_process(gen_data_teacher_score, eps, t)` → **gen and real share the same eps and t**.
- `fake_score_x0 = fake_score(perturbed_data, ...)` (unless `forward_kl=True`, which uses the teacher_score branch).
- Teacher conditional branch: `teacher(perturbed_data_teacher_score, ...)`.
- **CFG**: `_apply_classifier_free_guidance(perturbed_data_teacher_score, ...)` → **the unconditional branch is also evaluated at the noised real point**. Formula `x0 = x0_cond + (w-1)(x0_cond - x0_uncond)`, `w = guidance_scale = 5.0`.
- `vsd_loss = variational_score_distillation_loss(gen_data, teacher_x0, fake_score_x0, forward_kl_ensemble)` → **Task: read `fastgen/methods/common_loss.py` and write what changes when `forward_kl_ensemble=True` (the code has a `TODO: here do the minus signal change` comment) into `runs/NOTES_code_reading.md` for me.**
- Multi-step student (`student_sample_steps>1`): `input_student = forward_process(real_data, eps_student, t_student)` with `t_student` sampled from `t_list` → **the student's input at intermediate steps is a noised dataset sample, not its own rollout**. Also read `gen_data_from_net` and record in the same note whether the student takes one step or runs the remaining steps. This means switching to real-world data also changes the student's input distribution. Every experiment's NOTES must discuss the possible effect.
- In `build_model`, `fake_score` is **copied from the teacher**; `discriminator` is **randomly initialized** when `gan_loss_weight_gen>0` `[VERIFIED]`.

### 2.5 Memory-adaptive frame count (OOM → reduce frames automatically)

Frame count is the main memory lever, but it also changes the experiment itself (temporal variance, motion metrics). So **adjust it only in a probe before training; never mid-training**.

**Frame ladder (latent T → pixel frames):** `21 (81f) → 16 (61f) → 13 (49f) → 9 (33f) → 5 (17f)`. Start at 21 (DFD default); floor is 5; never go below.

**Write a probe script `scripts/probe_frames.sh` (or `.py`):**
1. For each T on the ladder (largest first), run the experiment's full config: set `trainer.max_iter` to the minimum that covers **both a student step and a fake_score step** (they alternate via `student_update_freq` and peak differently), plus one student step where replacement happens (DFD replacement costs an extra teacher forward). If F2's JVP / double-gradient diagnostics are on, trigger each once in the probe too.
2. Catch `torch.cuda.OutOfMemoryError` (and NCCL crashes caused by OOM); record `torch.cuda.max_memory_allocated()` per GPU.
3. Pick the largest T that runs **with peak ≤ 90% of GPU memory** (headroom for length variation and fragmentation).
4. Write `runs/FRAMES_LOCK.md`: GPU model and count, peak memory / OOM per T, chosen T. **Show me before locking.**

**Before reducing frames, try these semantics-preserving savings in order (re-probe after each):**
1. `dataloader_train.batch_size` 2 → 1. Global batch stays 16; FastGen recomputes grad accumulation. **No effect on the experiment.**
2. Confirm activation/gradient checkpointing is on (check `Wan_1_3B_Config`'s `disable_grad_ckpt` default and FastGen's SAC options).
3. Still OOM → step T down the ladder.
4. Still OOM at T=5 → try `trainer.fsdp_cpu_offload=True`; if that fails, stop and report. Never go lower.

**Locking rules:**
- All experiments in one results table (E0–E5) use **the same T**. Lock it from the most memory-hungry experiment in the set (E4 inversion and F2 diagnostics add memory).
- OOM mid-training: stop and report. **Never switch T and resume from a checkpoint.**
- Eval videos use the same T. The starting checkpoint was trained at T=21; if the locked T < 21, also evaluate E0 at T=21 as a reference row, labeled with its frame count.
- Crop all data (ViPE and real) to the chosen `sequence_length`: random start for training, fixed (middle) start for eval and diagnostics. Drop videos shorter than that and record the drop rate.

**Length-consistency check (required if locked T < 21):** rerun E1 and E2 at a longer T (or on more GPUs). Confirm "E1 vs E2, which is better" holds at both lengths, and compare F2's `reg_var` and `delta_sq` across lengths to quantify how frame count affects real-data variance. Record in `RESULTS.md`.

### E4b — (optional, Notion CoT 2.2.ii) + DFD + real data + minibatch OT
- Notion idea: draw a batch of x_real and z, re-match them so every pair x − G(z) is minimal.
- Two implementations `[ASK ME]`:
  - (a) exact: cost `C_ij = ‖x_i − G(z_j, c_i)‖²`, needs B² student forwards, expensive;
  - (b) approximate: cost `C_ij = ‖x_i − z_j‖²` (OT-CFM style), reorder noise before generation.
- Solver: `scipy.optimize.linear_sum_assignment`.

## 5. Known risks of the starting checkpoint (address each in NOTES)

1. The released checkpoint is most likely net-only: fake_score becomes a teacher copy, discriminator is random. That is not equivalent to the authors continuing from mid-DMD2 training with a trained critic, so E1 may fail to reproduce `ours_wan_t2v_vipe/0000040`.
2. The authors' DFD result used only 40 steps. With so few steps, results are sensitive to critic init, seed and data order; use multiple seeds in the reproduction check.
3. The start was trained at T=21 (81 frames). If §2.5 locks a smaller T, training length differs from the start's; validate conclusions with the length-consistency check.
